# EverDash v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Delegate only if the user authorizes delegation.

**Goal:** Turn the existing dashboard into EverDash, an installable HA OS app with runtime JSON management and paired legacy-device access.

**Architecture:** Retain the legacy-compatible Preact frontend and domain stores. Add a Node backend with separate trusted Ingress management and direct HTTPS dashboard listeners, persistent validated JSON, a restricted HA adapter, and revocable device sessions. Publish prebuilt HA app images; standalone onboarding is deferred.

**Tech Stack:** Preact 10, TypeScript, CSS Modules, Vite legacy build, browser XMLHttpRequest, Node.js 24 LTS, Fastify, Node crypto/filesystem/HTTPS, Node test runner, Playwright, Docker Buildx and GitHub Actions. Pin backend dependency versions after checking official compatibility documentation during implementation.

**Spec:** [EverDash v1 design](../specs/2026-10-19-everdash-v1-design.md). Read both documents before implementation. The spec defines all route shapes, constants, storage behavior, and access boundaries.

## Global constraints

- Production browser target remains iOS 12 and Safari 12; legacy bundles and the service worker remain ES5.
- Preserve existing components, explicit entity IDs, polling, cancellation, optimistic command ordering, translations, unavailable states, and `my-home:preferences:v1`.
- No HA credentials in frontend builds, runtime dashboard JSON, URLs, logs, exports, or offline caches.
- Management is available only through trusted HA Ingress; a paired device is never a manager.
- First release has JSON editing only. Do not add visual arrangement, OAuth, independent accounts, or standalone onboarding.
- Keep development and tests isolated from real HA credentials and devices. No intermediate unauthenticated server is released.
- Use braces for conditionals and the repository's lint/format rules. Add focused modules instead of growing App.tsx or creating one monolithic server.
- This task produces a plan only. Implementing code, publishing images, changing repository visibility, and rewriting Git history are separate work.

## Review focus

- Forged Ingress headers arriving on the public listener must never grant management access (tasks 3–4).
- A crash or concurrent editor must not corrupt or silently overwrite the published configuration (task 2).
- An obsolete tablet must not control removed entities after a configuration update (tasks 3 and 5).
- Nested Ingress paths and Safari/Home Screen storage separation must not break setup or pairing (tasks 4–6).
- Missing certificates and corrupted persisted data must leave a usable management recovery path (tasks 2 and 6).

## Task 2: Build persistent configuration and recovery

**Files:** Create `server/config/{repository,revision}.ts`, server TypeScript/build configuration, and `tests/server-config.test.ts`. Update package scripts to typecheck/build the server separately from browser output.

**Interfaces:** `ConfigSnapshot = {revision: string, config: DashboardDocument}`. `ConfigRepository.read(): ConfigSnapshot | null`, `validate(input: unknown)`, `save(baseRevision: string | null, input: unknown): Promise<ConfigSnapshot>`, and `readPrevious(): DashboardDocument | null`. First publication uses null baseRevision. Repository publishes a change event after durable successful writes.

- [ ] Test default empty-view initialization, saved revision stability, invalid input, stale-revision rejection, previous-version retention, restart persistence, concurrent saves, interrupted writes, unwritable storage and recovery from each corrupt-file combination.
- [ ] Implement canonical revisions, serialized writes, restricted file permissions, temporary file cleanup and the spec's fsync/rename transaction. Inject filesystem fault points for crash/failure tests.
- [ ] Keep invalid storage from starting polling; expose a recoverable configuration diagnostic. Do not overwrite corrupt files with examples when recovery requires user action.
- [ ] Run server/config tests and typecheck; confirm failed saves keep both the in-memory published revision and working dashboard intact. Commit as `feat: persist validated dashboard configuration`.

## Task 3: Add the backend and constrained Home Assistant adapter

**Interfaces:** `buildApp(dependencies, listenerMode: 'management' | 'direct')` creates routes without listening; authorization dependencies default to deny. `createClient(baseUrl: string)` implements the existing CatalogApi/ClimateApi contracts using relative same-origin XHR. Inject a stable client factory into feature hooks; do not share cancellation ownership across independently stopped stores.

- [ ] Test default-denied routes, configured-only state reads, full-catalog filtering, each existing service payload, weather response passthrough, invalid extra fields/targets, upstream 401/403/404, timeout, malformed responses, cancellation, and no automatic write retry.
- [ ] Implement fixed Supervisor upstream access using its server-only token and bounded responses. Commands target only current published configuration; authorize every request, including after a config change.
- [ ] Add the two-listener route boundary, safe relative asset serving, exact-origin mutation checks, required custom request header, redacted logs and no-store API headers. Do not expose an arbitrary proxy or direct management route.
- [ ] Replace all frontend VITE credential reads and old credential-related error messages. Preserve store behavior and independent abort lifetimes; keep fake server credentials confined to isolated fixtures.
- [ ] Run existing HA/store tests plus new HTTP policy tests. Inspect a fixture production bundle for absence of token values and credential environment names. Commit as `feat: route dashboard controls through the backend`.

## Task 4: Implement pairing, sessions and trusted management access

**Files:** Create `server/auth/{ingress,pairing,sessions,rate-limit}.ts`, device repository module, `src/features/pairing/` UI/data modules, and `tests/pairing.test.ts`/HTTP authorization fixtures.

**Interfaces:** Implement the design's pairing/session endpoints exactly. Management principal is the nonempty HA user ID on the trusted internal listener; direct principal is a nonexpired, nonrevoked opaque cookie session. No principal is inferred from a device label, request code, URL, or direct forwarded header.

- [ ] Add failing tests for forged headers and wrong peers, missing Ingress user ID, public management access with a valid device cookie, successful approval, independent poll-secret validation, five-minute expiry, replay, duplicate redemption, restart and revoked/expired sessions.
- [ ] Implement random codes/secrets, digest-only persistent sessions, one-time cookie issuance, device labels, logout and revocation. Apply exact creation/approval/poll limits, capacity and Retry-After behavior from the design.
- [ ] Build the tablet pairing screen and Ingress approval/device list with native controls, EN/PL copy, accessible status updates, retry and expiry behavior. Require explicit pairing initiation; no automatic request on every page reload.
- [ ] Add browser coverage for pairing, blocked storage/session loss, logout, immediate next-request revocation, unknown-device bootstrap and no API requests before authorization. Record Safari-to-Home-Screen storage testing for physical verification.
- [ ] Run authorization, pairing and browser fixtures. Confirm cookie flags and no secrets in API lists, logs or URLs. Commit as `feat: pair and revoke dashboard devices`.

## Verification and handoff

After each source task run `npm run format`, `npm run lint`, `npm run format:check`, and `npm run typecheck`, including server typechecking once introduced. Run focused existing/new tests for the task. For production/browser changes run a fresh `npm run build` then `npm run check:compat`; run the full `npm test` and `npm run test:browser` at integration milestones and final release verification.

The final acceptance report must separately state automated results, image/HA OS installation results, and physical iPad results. Tests never actuate the real home. No feature is complete merely because a modern browser passes.

Review this plan and its design before implementation. Recommended execution is sequential in the current chat because configuration revisions, server policy, sessions and frontend store lifetimes share interfaces. Public-release blockers are license confirmation, actual registry coordinates, a clean publication audit, and deployment/hardware acceptance evidence; these do not block local implementation.
